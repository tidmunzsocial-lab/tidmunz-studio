# Auto video supervision, root-cause diagnosis, and cross-chat continuity

**Standing owner instruction, verified 2026-11-07:** When the user authorizes one Auto production, continue its existing flow to an actually verified output without making them repeat routine steps or ask whether it stopped. This is a workflow obligation **within available tools and authorizations**, not a claim that a skill runs independently or that ChatGPT can remain live after a chat ends. Install/confirm a local deterministic watcher and, where available, a scheduled ChatGPT automation for out-of-session checks. Don't wait for the user to spot a stop. When the watcher detects a stop, repair *only* a proven safe cause; if root cause is unknown, retain the receipts and report that block instead of looping.

## 1. Verify and attach to the current job, never invent a new one

1. Find the **specific authorized device** afresh via device-routing (verify device identity, running app, source machine and project). No personal hostname, Device ID, account, URL or secret is embedded in this skill.
2. Call the **real local app operator/status API**, preferably `snapgen_modules/snapgen_ai_operator.py status` and `diagnose` via verified Remote Desktop Commander or the connected TailScale shell. Local Mobile Web usually serves on `127.0.0.1:8765`; resolve credentials on **that device** and never expose them. Check `app_ready`, exact `story`, `auto_busy`, `stage`, `detail`, `percent_ui`, images/clips, provider Slots, `final_ready`, `final_file`.
3. Read existing `project.json`, selected original full script, selected narration, real audio duration, matching story Context and references, actual scene files and receipts. Use existing project, do not reset or recreate it when opening a new ChatGPT conversation. For a short voice test keep the **full original story** with the short narration; native Auto aligns/extracts the spoken part.
4. **Installed source differs by version.** Auto v2.0.16+ introduces stages `analysis → context → ref_characters → transcribe → plan → storyboard → images → motion → clips → video`, automatically makes same-story Context and character/location Refs, and binds the Image AI Ref folder. Older releases require manually preparing Prompt-Ref and Ref. Read **installed** `VIDEO_STAGES`, `stage_context`, and `stage_auto_ref_characters` at runtime. The older companion `tidmunz-auto-workflow` description of eight stages is version-scoped, not an instruction to manually redo those steps on v2.0.16+.
5. If `auto_busy=true`, monitor the actual current stage; **never send another start**. If `false`, classify the stop and inspect cloud provider receipts/UUID before any paid resume. `202/pending` uses the **same request ID** with the receipt endpoint. Stop/restart/retry provider clips only if verified safe. Never redo successful images or clips.

## 2. Start a watcher automatically for user-authorized unattended production

- When the user wants 'finish without asking me again', create/verify a **single-instance native watcher** for this exact project, if a supported local or scheduled execution mechanism is available. A verified example is a Python watcher using the on-device operator, writing `snapgen_data/logs/<project>-watch.json` plus event history; **20-second local polling** was tested on 2026-11-07. The watcher must contain the selected project identity, detect project switches, write latest status atomically, guard duplicate processes with a lifetime lock, and verify an output before declaring success. A task at Windows logon may restart the watcher after reboot but cannot keep the computer awake or recover a disconnected device.
- Don't install multiple watchers just because the chat is new. Inspect existing watcher process, state log, last poll, logon task, and attempt journal first. A stale JSON file is not proof of an active watcher. A healthy program's long GPT response is not automatically a failure.
- When connected task/automation tools support scheduled checks, configure them for the user-requested follow-up; **ChatGPT automations have their own minimum cadence (hourly for checks), not the native 20-second cadence**. Say which part is a deterministic local process and which is a periodic ChatGPT model execution. Never claim to have a live AI repairing tasks between visits unless an actual connected persistent agent exists and has been verified.
- Persist the exact story, current stage, error class, last progress change, watcher timestamp, attempt count, last command ID/receipt, and next safe action in an accessible project state/journal. A new chat must start by reading it and the app's current status; do **not** ask the user to repeat standing directions.
- Notify only on important progress/stops/final output. If the user returns before an automation check, diagnose immediately instead of saying to wait for the hourly timer. Resume only after preflight.

## 3. Diagnose ChatGPT Chrome Bridge `404 conversation_not_found` at the source

**Evidence from 2026-11-07 (v2.0.16):** The selected Auto project stopped at Context 2%. Two fresh story-history attempts succeeded at ingesting FULL STORY and running independent analyst A and B, but failed when the **judge tried to continue the original story conversation**. The extension reported `ChatGPT conversation failed: 404 — ChatGPT cannot load this chat`; the local bridge surfaced `chatgpt_conversation_not_found`. A reset-and-restart alone reproduced the failure. No images/clips were present. **These observations establish failure to retrieve/continue the primary ChatGPT conversation; they do NOT yet prove why the ChatGPT service lost it.** Never call this fixed merely because a one-time retry was coded.

Trace every layer, keeping credentials out of logs:

1. At the Auto `context` stage, identify the exact failed operation in app console + status, and whether failure is **before** or **after** actual GPT message delivery. Compare `send_state`, worker receipt, HTTP status and provider-error text. If the cloud result may have been sent, do **not** blindly resend paid work.
2. Inspect the current story's `snapgen_data/meta/prompt_ref_conversation.json`: `story_hash`, presence of `conversation_id`, `parent_message_id`, `context_ready`, and account alias. Compare normalized hash to `prompt_ref_source.txt` and the actual selected DOCX. **Never print the raw IDs, token, account/email or entire story into the chat.** A nonempty cursor is not evidence that the backend can load it.
3. Trace `snapgen_gui_v2.py::_prompt_ref_chat` → `snapgen_chrome_api.py::chat_job` → `chrome_ext/background.js::runJob`/`pageSendInner`. The extension routes to `https://chatgpt.com/c/<conversation_id>`; an unready DOM plus an `Unable to load conversation` screen, or authenticated `GET /backend-api/conversation/<conversation_id>` 404, yields the current error. Distinguish a **real provider 404** from a local API endpoint typo, 401/403, 429, timeout or lack of Chrome extension connection. A 404 after pressing Send is not proof the entire job was never billed; inspect send state.
4. Compare the **actual Chrome logged-in identity, browser/profile, created chat URL, verified post-send conversation route, cookie/session health, and the identity to which the story is pinned**; a story created under another account cannot be continued under the current one. Check whether a fresh chat is persisted/readable **after** creation and again before its judge turn. Check browser extension worker tab/reload timing, provider consistency, context durability and exact redirect. Do this through supported read-only app diagnostics and the browser UI; do not expose credentials or copy ChatGPT cookies into a model prompt.
5. If only a **fresh, unsaved Context** history failed, with same-story hash and **no refs/images/clips, no pending paid receipts**, back up the exact history metadata and source, reset **only that story's invalid GPT cursor**, reopen in the same account, ingest the original full story, and try the Context analysis **at most once**. Prefer the native guarded recovery in source commit `b2ea9e8` / `snapgen_prompt_ref_history_recovery.py` **after checking that it was actually installed**; the commit itself does not update a running desktop process. Verify the next judge turn, Context sidecar, char/location refs and actual stage progression. Do not reset a history with `context_ready=true` or a mismatched story.
6. **If the exact 404 recurs after a new chat, STOP resetting.** The evidence implicates chat persistence/account/Chrome worker behavior more than an old stale cursor. Gather sanitized response status, actual route, account match and extension logs; produce a reproducible test with one newly created, non-paid text chat before developing another fix. Never loop forever, silently substitute a different story or provider, or claim final output. Fix and regression-test the true failing layer (e.g. verify persistence/identity before storing a cursor), then install the release and verify against a live run.

**Status distinction:** A source patch can be merged, compiled and unit-tested while the installed application remains the previous binary. Confirm application version/process restart and observed live behavior before reporting a 404 issue as resolved. If repeated 404 cannot be resolved in an authorized scope, report the precise blocker and safe next step without requiring the user to repeatedly discover the stop.

## 4. Resume and completion safety

- Resume from the saved stage only when the app is idle, authorized for this exact job, no duplicate pending generation, and the project still matches. After any recovery, follow `analysis/context → character/location refs → select same-story folder → speech/storyboard/images/clips → render` in the **actual installed version**; no manual Image AI attachments on new Auto once the ref-folder binding was verified.
- If work stops mid-ref/image/clip, count files and receipts and **resume missing work only**. Follow provider's rate/capacity statuses. Never turn a watcher into an uncontrolled paid retry engine.
- Long-running activity should not silently end because a chat turn ends. Delegate deterministic checks to the verified local watcher, optional future-task automation, and record state. A current interactive agent can only continue actively while its turn/tool execution remains active.
- Complete only when final media exists, nonempty, is playable, expected duration/resolution and audio are verified and the app indicates completion. Include location/format and remaining warnings. `100%`, `pending`, `busy=false`, or queued is not completion.

## 5. Skill learning is part of finishing the job

- Whenever a new repeatable recovery, root cause, provider behavior or useful app API path is **verified**, immediately update the **installed plugin skill** through the available plugin editing mechanism without asking the user to remind you. Read the existing skill/version, preserve unrelated instructions, publish a guarded incremental release, and read back version/content. Do not call a local draft a published skill.
- For unverified theory, add to a clearly marked investigation checklist, not as guaranteed behavior. Never put fixed machine identities, addresses, emails, URLs with secrets, or tokens in a published skill. These instruction updates do **not** themselves authorize application-code edits, publish releases, or spend credits.
